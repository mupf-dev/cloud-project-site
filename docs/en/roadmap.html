Built in-house – and when not#

The project's guiding principle: whatever controls the platform, BYOC builds itself – in Rust, fitting the shared Raft state, the permission model and the parity of API, portal and MCP. Existing solutions are integrated only with a reason, where maturity, security or maintenance effort do not justify building our own: Linux kernel features, the hypervisor, container runtimes, database and storage engines with a high maintenance burden, and supply-chain checking tools. Integrated components run behind clear process boundaries. This page names Rust libraries only where they carry significant weight. The full assessment per feature is in the hyperscaler feature analysis.

What has been achieved#

Everything in this section is implemented and verified at least in an automated lab. Where verification on real hardware is still pending, this is stated.

OS image and boot (cpOS)#

DoneIn-house + integrated

An immutable node operating system for amd64 and arm64 (UEFI). /usr is read-only and protected against tampering with dm-verity; there are two slots (A/B) for updates. Kernel, initrd and command line are packed into a signed unified kernel image, signed with the project's own Secure Boot keys. The state partition is encrypted with LUKS2 and bound to TPM 2.0; without a TPM only the "homelab" profile with a passphrase is allowed. After every boot a health gate checks whether the node is healthy – otherwise the boot loader falls back to the previous slot after three attempts. Out of the box there is no login, no SSH and no package manager; inbound traffic is denied by default.

  • In-house: image definition, partition layout, hardening profile, operating modes, health gate.
  • Integrated: Debian packages, the Linux kernel (dm-verity, dm-crypt/LUKS2, TPM 2.0), systemd (systemd-boot, systemd-repart, systemd-sysupdate), mkosi as the build tool, AppArmor, nftables.
  • Verification: end-to-end boot tests in QEMU for both architectures with an emulated TPM; automated hardening checks in the booted image. A first node runs on a used business notebook. Raspberry Pi support is prepared but not yet tested on real hardware.

More: OS image.

Network boot service#

Done (lab)In-house + integrated

The boot service cp-bootd runs as a role on cluster nodes and complements the existing DHCP server instead of replacing it (proxyDHCP). It handles PXE for BIOS and UEFI, UEFI HTTP boot, iPXE and – in preparation – Raspberry Pi network boot. All artifacts are checked against a signed boot manifest. Several boot services can run in parallel.

  • In-house: DHCP and TFTP handling (own lean parsers), boot decisions, manifest.
  • Integrated: iPXE as the network boot loader (built and signed by the project).
  • Verification: a QEMU boot lab with two boot services in a simulated home network; fuzz and property tests for the parsers. Network boot on real hardware is the next step.

More: Boot and adoption.

First node, adoption and installer#

DoneRefinements in acceptanceIn-house + integrated

The first node boots from a USB stick; a setup wizard guides through region, portal address and the first administrator (invitation plus passkey) via portal, API or MCP. New nodes report as "waiting" and are approved – manually or by an auto-adopt rule. Roles are assigned declaratively and applied by a reconciler. The installer writes cpOS to the internal disk following fixed rules: never onto the boot medium, foreign data only after explicit confirmation, TPM binding and re-signing with the installation's own key. Nodes can be decommissioned and replaced, even across cell boundaries.

  • In-house: setup wizard, adoption flow, role model, installer including UEFI boot entries.
  • Integrated: systemd-repart (partitioning), LUKS2 (encryption).
  • Verification: QEMU installation from the stick with and without a TPM; container labs for adoption and roles; running as the first node on real notebook hardware. Refinements to the setup wizard are implemented and in acceptance.

Control plane: Raft, gossip, cells#

DoneIn-house + library

cp-agent runs on every node. Membership spreads via gossip; the authoritative state lives in one Raft group per cell. Even two nodes plus a witness that holds no payload data are fault tolerant; the control group is elected automatically. Witnesses write signed checkpoints so that a node that has been rolled back is detected. The scheduler places workloads by architecture (ARM/x86), resources and node pools.

  • In-house: cell and witness model, control group election, state machine, scheduler, node lifecycle.
  • Libraries (load-bearing): openraft (Raft consensus), foca (SWIM gossip), redb (local storage).
  • Verification: deterministic simulation with fixed random seeds (up to 1,000 seeds per scenario without invariant violations) and container labs with multi-node clusters.

More: Control plane.

Node identity and cryptography#

DoneIn-house + library

An internal certificate authority issues an identity to every node; nodes talk to each other only via mutually authenticated TLS. Algorithms follow selectable crypto profiles aligned with BSI TR-02102. Privileged tasks are handled by a narrow root helper, cp-privd, with a fixed set of commands; the agent itself runs without root privileges.

  • In-house: PKI workflows, crypto profiles, root helper, central crypto interface.
  • Libraries (load-bearing): rustls (TLS), aws-lc-rs (cryptography), rcgen (certificates).
  • Verification: unit and fuzz tests, container labs with mTLS between all nodes.

More: Security model, Cryptography.

Identity and tenants#

Identity service doneTenants plannedIn-house + library

A purpose-built OIDC/OAuth 2.1 authorization server runs as the identity role. Sign-in is by passkey (WebAuthn) only; on top of that come authorization code with PKCE, device flow for the command line, token revocation, DPoP and rate limits. Signing keys live only in the separate cp-identityd process. API, portal, cpctl and MCP all use the same tokens.

  • In-house: authorization server, passkey verification, token and session management.
  • Libraries: aws-lc-rs (signatures) via the central crypto interface.
  • Verification: container labs with end-to-end sign-in flows; browser tests with a virtual passkey against a real agent.
  • Still open: tenants, projects, groups, permission model and quotas – see Towards the MVP.

More: Identity and permissions.

API, portal, MCP and CLI with parity#

DoneIn-house + library

Every agent serves the resource API (REST, OpenAPI) and forwards requests to the responsible node. The cpctl command line and the MCP server for AI agents are derived from the same schema. The web portal is served by the node itself, shows changes live and is reachable via several nodes. A parity check in CI ensures that every mutating operation is available in all access paths.

  • In-house: resource model, API, forwarding, cpctl, MCP tools, portal, parity check.
  • Libraries (load-bearing): axum/hyper (HTTP), rmcp (MCP protocol), Svelte and Vite (portal).
  • Verification: container labs, browser tests of the portal, parity check in every CI run.

More: API-first, Portal.

Updates and releases#

In acceptanceIn-house + integrated

A release is a signed bundle of OS image, services and SBOM. The signature chain follows the TUF pattern (several roles, root rotation, rollback protection). Releases are imported rather than fetched online, and at least two nodes hold them for distribution. Nodes write the new release into the free A/B slot and reboot; the health gate confirms it, or an automatic fallback follows. An update controller rolls out node by node, protects the Raft quorum, updates the leader last and pauses on errors. A plan preview shows the order and impact beforehand.

  • In-house: release format, verification of the signature chain following the TUF specification, import and distribution, update controller.
  • Integrated: systemd-sysupdate (writing the A/B slot), systemd-boot (boot counting, fallback).
  • Verification: QEMU labs for import, node update and rollout. End-to-end acceptance with rollout and rollback, plus a real update on hardware, come next.

More: Release bundle, Rollout.

Platform DNS#

In acceptanceIn-house + library

The cluster manages its own DNS zone: cp-dnsd answers authoritatively from the Raft state, with DNSSEC if desired. Two fixed virtual IP addresses are assigned via a Raft lease (VRRP-like, built in-house). The existing DNS server on the network only needs a forwarder or a delegation to these addresses.

  • In-house: DNS server logic, zone building, DNSSEC signing, assignment of the virtual addresses.
  • Library: hickory-proto – only for the DNS wire format.
  • Verification: container lab with a multi-node cluster. Failover of the virtual addresses will be measured in the two-node hardware test.

More: Platform DNS.

Network: WireGuard underlay#

Underlay doneTenant overlay plannedIn-house + integrated

Every node builds its encrypted underlay on its own, with no configuration by the operator: a key per node, signed announcements via the cluster state, full mesh per site, relays between sites and for nodes behind NAT, key rotation without dropping connections. In addition, a pre-shared key derived from a hybrid key exchange (classical plus ML-KEM) protects against later decryption by quantum computers.

  • In-house: topology planning, key distribution and rotation, netlink control via the root helper.
  • Integrated: WireGuard in the Linux kernel.
  • Verification: container labs with multi-node clusters and simulation of the topology.

More: Network.

Storage#

Concept decided, implementation plannedIn-house + integrated

The storage concept is decided: a purpose-built block store, cp-blk, for 2 to more than 1,000 nodes (local first, replicated only after a maturity gate), and S3-compatible object storage with Garage behind a purpose-built S3 front end. So far, only the nodes' encrypted state partition is implemented.

More: Storage.

Supply chain and compliance#

DoneIntegratedOwn rules

Every CI run checks formatting, lints, tests, licenses and sources of dependencies, security advisories, REUSE compliance and the parity and compliance rules. SBOMs (CycloneDX and SPDX) and VEX documents are produced for binaries and the OS image; releases carry signatures and provenance attestations. Reproducible builds have been demonstrated for x86_64 and aarch64. A vulnerability process with coordinated disclosure is in place. Requirements from BSI IT-Grundschutz and ISO standards are mapped to components – this is preparation, not certification.

  • Integrated: cargo-deny, cargo-audit, the REUSE tool, cargo-cyclonedx, cosign, OpenSCAP.
  • In-house: policy-as-code rules, parity and compliance checks, SBOM generation for the OS image.

More: Compliance by design, Vulnerability management.

Test and lab infrastructure#

DoneIn-house + integrated

  • Deterministic simulation of the cluster with fixed seeds; a run can be repeated exactly and reports the first diverging step (in-house, on the turmoil library).
  • Container labs with multi-node clusters; every lab is checked against a target table and is part of acceptance (in-house).
  • End-to-end labs in QEMU with UEFI firmware and an emulated TPM for boot, installation, network boot and updates (integrated: QEMU, OVMF, swtpm).
  • Browser tests of the portal with a virtual passkey (integrated: Playwright).
  • Real hardware: a used business notebook as the first node. More notebooks and Raspberry Pi will follow.

Towards the MVP#

Target: Q2 2027. The MVP is a complete small cloud for the homelab: tenants create resources on their own – via portal, API and MCP.

  • Tenants and permissionsIn-house + library

    Tenants, projects, users, groups, API keys, quotas, audit log. Permissions as an in-house relationship store plus a policy language.

    Integrated: Cedar (policies)

  • Sign-in to VMs and containersIn-house

    Log in with the platform identity right into the guest OS; roles become permissions inside the guest.

  • Tenant networksIn-house + integrated

    VPCs and subnets as an overlay inside the encrypted underlay, IPAM, DHCP, internal DNS, security groups, NAT, floating IPs, load balancers.

    Integrated: Linux kernel (VRF, VXLAN, nftables)

  • Virtual machinesIn-house + integrated

    Lifecycle, images, cloud-init, console in the portal – own control logic on top of a proven hypervisor.

    Integrated: Cloud Hypervisor

  • Container instances and registryIn-house + integrated

    Individual containers with microVM isolation, one registry per tenant.

    Integrated: container runtime and microVM (candidates: containerd, youki, Kata Containers), zot

  • Managed KubernetesIn-house + integrated

    Kubernetes clusters per tenant; BYOC itself handles creation, upgrades and node pools.

    Integrated: k3s

  • Block volumes (local)In-house + integrated

    Purpose-built block store cp-blk with snapshots and per-tenant encryption.

    Integrated: Linux kernel (dm-thin, dm-crypt)

  • Object storage (S3)In-house + integrated

    Buckets per tenant behind a purpose-built S3 front end with permission checks.

    Integrated: Garage

  • Key managementIn-house

    Key hierarchy per tenant and encryption of data at rest.

  • ObservabilityIn-house + integrated

    Collection, alerts and dashboards in the portal are built in-house; data is stored in proven time-series and log stores.

    Integrated: VictoriaMetrics, log store (under evaluation)

  • OperationsIn-house

    Backup and restore of the control plane, business continuity and recovery concept, usage metering, update policies and maintenance windows.

  • Security evidenceIn-house + integrated

    Control matrix and evidence export for operators, external penetration test before the MVP.

After the MVP, the API groups move from v1alpha1 via v1beta1 to v1.

Quality gates#

  • Phase 1 gate: fault tolerance (two nodes plus witness, no single point of failure from three nodes up) is demonstrated in a deterministic simulation with 10,000 random seeds without invariant violations and on real hardware. The simulation already runs with up to 1,000 seeds per scenario; the full run and the hardware proof are still pending.
  • Before every phase gate: tests on real hardware (Raspberry Pi, notebooks, servers).
  • Before every minor release: Jepsen-style consistency checks.
  • Before tenant data on replicated volumes: maturity gate with simulation, fault injection, long-running tests, recovery test and external review.

Non-goals#

BYOC builds no hypervisor of its own, no distributed file system from scratch, and does not use Kubernetes as the foundation of the platform. Proven open-source components are integrated behind clear process boundaries. More on this in Vision, terminology and scope.
