Services like a hyperscaler#

The platform offers core services modeled on the well-known public clouds. All services are resources of the same API and can therefore be used equally through the portal, the API and MCP.

Three equivalent access paths#

Every feature is available through the REST API (OpenAPI), the web portal and MCP (Model Context Protocol, for AI assistants and agents) – at every level: platform, tenant, project, resource. The portal and the MCP tools are derived from the same API schema; a CI check prevents any access path from gaining features the others lack. In addition there is the command-line tool cpctl. Details: API-first principle.

yaml# Example resource (simplified)
apiVersion: compute.cloud-project.io/v1
kind: VirtualMachine
metadata:
  name: web-01
  parent: cp:global:tenant/acme/project/shop
  labels: { env: prod }
spec:                       # desired state
  machineType: small-2c-4g
  arch: any                 # arm64 | x86_64 | any
  image: cp:global:image/debian-13
  network: { vpc: default, subnet: web }
status:                     # actual state, written only by the system
  phase: Running

Node lifecycle#

A node goes through a clearly defined lifecycle. Unknown hardware never automatically gets access to tenant data – only adoption assigns it an identity.

  • Discover: A new node boots over the network (PXE/HTTP boot, Raspberry Pi network boot) or from a USB stick into an in-memory discovery system. It writes nothing to disks and reports a hardware profile.
  • Adopt: Approval via portal, API or MCP – protected by a confirmation code and, at higher expansion stages, additionally by TPM attestation. The node's private key never leaves the node.
  • Provision: Installation of the signed OS image (or diskless operation), issuance of the node certificate, admission to the underlay network and gossip.
  • Operate: Assign roles, maintenance with drain, self-healing on faults.
  • Retire: Verifiable erasure, revocation of the certificate, rotation of the gossip keys – with proof of erasure for compliance.

Updates and releases#

  • Immutable OS image (cpOS): /usr is read-only and protected by dm-verity, / is ephemeral, state lives in an encrypted partition.
  • A/B updates with automatic rollback: The update is written to the inactive slot. The new version only takes effect once a health gate reports green after the reboot; otherwise the node falls back to the old slot on its own after a few attempts.
  • Signed release bundles: Images, extensions and the agent are delivered as a bundle with a manifest, checksums, SBOM and signatures; update metadata follows the principles of TUF (The Update Framework) with offline root keys.
  • Rollout controller: Updates roll out in waves with a canary stage, maintenance windows and maxUnavailable. At most one voter per cell is updated at a time, the leader last. If a gate fails, the rollout stops.

More: OS image · Rollout · Release bundle · Release signing.

Platform DNS#

The dns role (service cp-dnsd) answers authoritatively for the names of the platform and the tenants, signs zones with DNSSEC, assigns virtual IP addresses (VIPs) for platform services such as the portal and the API, and protects itself against abuse with rate limiting. Within tenant networks, every host answers DNS, DHCP and metadata locally – with no central service in the data path. More: Platform DNS.

Identity and tenants#

  • Hierarchy platform → tenant → project → resource, optionally with folders inside a tenant.
  • A dedicated, lean OIDC/OAuth 2.1 authorization server with passkeys first and federation with existing identity providers (OIDC/SAML).
  • Short-lived, sender-constrained tokens that are verified locally on every node. Authorization via a Zanzibar-style relationship store plus Cedar policies for conditions and guardrails.
  • Strict separation between operator and tenant content: operators see metadata; content only through a justified, time-limited and logged access request.
  • AI agents are a separate actor type; they act with the intersection of user permissions, token scope and agent guardrails.
  • Tenant deletion with crypto-shredding and a signed proof of deletion.

Storage#

  • Block volumes over a dedicated Rust data path: local (dm-thin + dm-crypt) and replicated (two to three copies) – the same path from 2 to thousands of nodes.
  • Metadata in the cell's existing Raft group; user data never goes through consensus.
  • Tenant encryption on the compute node: storage nodes only see ciphertext.
  • Object storage, S3-compatible, behind a dedicated S3 front end with permission checks and quotas.
  • File storage via NFS on replicated volumes, in the network of the respective VPC.
  • Placement across failure domains; a maturity gate before replicated volumes are used for tenant data.

More: Storage concept.

Network#

  • Underlay: one WireGuard interface per node, IPv6-only inside; peers come exclusively from the replicated state. Additionally, a pre-shared key from a post-quantum scheme.
  • Tenant overlay cp-vnet: its own control logic in the agent, Linux kernel data path (VRF per VPC, VXLAN inside the WireGuard tunnel, nftables) – no second consensus database.
  • Security groups are stateful, with inbound traffic blocked by default.
  • North-south traffic via the network-gateway role: NAT, floating IPs, L4 load balancers; advertised via Layer 2 in a homelab and via BGP in a data center.
  • Three expansion stages: flat (a single LAN), vlan, routed (L3 to the host).

More: Network architecture.

Security and compliance#

  • Chain of trust from Secure Boot with the installation's own keys through Measured Boot and TPM-bound disk encryption to mTLS between all services.
  • Node identity with short-lived certificates from an internal PKI, trust levels T0–T4, remote attestation.
  • Cryptography according to BSI TR-02102, crypto agility and a roadmap for post-quantum schemes.
  • Complete audit trail of every change, break-glass procedure with logging.
  • Compliance by design: 36 architecture guidelines, a requirements catalog drawn from ISO 27001, BSI IT-Grundschutz, BSI C5, GDPR, NIS2 and the Cyber Resilience Act; evidence becomes exportable.
  • Supply chain: reproducible builds, an SBOM per artifact, signed releases, VEX for vulnerability assessments.

More: Security model · Cryptography · Compliance by design.

AI-native platform#

  • A dedicated API group for models, model versions, inference endpoints, AI gateways, budgets, guardrails, vector indexes and knowledge bases.
  • Inference engines (llama.cpp first, then vLLM) run as signed containers behind a unified adapter; dedicated endpoints run in MicroVMs with a passed-through accelerator.
  • Two operating models: dedicated per tenant or shared/serverless with per-token billing – without a cross-tenant cache.
  • Accelerators (GPU, NPU) as a scheduler resource, scale-to-zero with a local model cache, models as signed OCI artifacts with a cache per cell.
  • The platform itself can be controlled via MCP; tenants' agents use platform tools with restricted permissions.
  • AI compliance as a cross-cutting concern: model cards, provenance, labeling, logging under the EU AI Act, mapping to BSI AIC4.
