Target picture#

BYOC (BYOC for short) is an open-source, decentralized cloud platform. It takes in arbitrary hardware – from a Raspberry Pi to laptops to rack servers – over a network cable and turns it into a multi-tenant cloud with the core services of a hyperscaler. It covers everything from a two-node homelab to a data center with thousands of nodes.

The short version for outsiders:

Plug in the cable – node appears – approve – assign a role – done. Everything via portal, API or MCP.

Guiding principles#

  1. Decentralized, no central controller. Every node runs the agent; portal, API and MCP run on the hardware they manage. If a node fails, another one takes over.
  2. API-first, three equivalent access paths. Every function at every level is available via API, web portal and MCP – including initial setup and adoption. The API is the single source of truth (see API-first).
  3. Zero-touch after the cable. Once plugged in, no screen, keyboard or SSH is needed. The only deliberate action is the approval (adoption) – or an auto-adopt rule. Auto-adopt is disabled by default and only permitted permanently with hardware attestation.
  4. Scales in both directions. Two nodes are a full-fledged operating mode, not a demo. Growth to thousands of nodes happens through cells and regions, without reinstalling.
  5. Heterogeneous from day one. ARM64 and x86_64 mixed; nodes with and without a BMC, with little and lots of RAM.
  6. Declarative and self-healing. The desired state is described; reconcilers bring it about.
  7. Immutable nodes. Image-based operating system with A/B updates; no manual maintenance on nodes (see OS image).
  8. Secure & compliant by design. mTLS everywhere, tenant isolation at every layer, logging of every change, exportable evidence for ISO 27001, BSI C5 and BSI IT-Grundschutz (see Compliance by design).
  9. Open source throughout. Only open-source dependencies; in-house components in Rust (see Rust stack and License governance).
  10. Integrate what is proven, build what is missing. No in-house hypervisor – the project builds the control plane, the automation and the unified interface.

Terminology (glossary)#

Infrastructure#

TermMeaning
PlatformAll regions of one operator taken together.
NodeA physical device running the agent; the smallest unit.
AgentRust service on every node: lifecycle, roles, local API/portal/MCP, request forwarding.
RoleFunction a node performs (e.g. boot, control, compute-vm). A node can have multiple roles. Roles are assigned, not installed.
Control groupSmall, automatically elected set of nodes (3 or 5) with the control role that holds a cell's state via Raft consensus.
Witness nodeLightweight node (e.g. a Pi) that only votes, so that two-node clusters have a quorum.
CellUnit of failure and scaling with its own control group (guideline: up to about 500–1,000 nodes). Cells fail independently of one another.
RegionOne or more cells at a site or federation sharing a network and a common region API.
SitePhysical location (homelab, data center room). Sites are connected via the WireGuard underlay.
FederationCombination of several regions under one global identity and API (later expansion stage).
UnderlayEncrypted WireGuard mesh between nodes – the platform's transport network.
Overlay / VPCVirtual, tenant-owned network on top of the underlay (see Network).
Boot serviceRole boot: proxyDHCP, iPXE/UEFI HTTP boot, Pi netboot, image delivery. Present multiple times, never a single point of failure.

TermMeaning
OperatorRuns the platform; manages hardware, regions and tenants.
TenantOrganizationally and technically isolated customer with its own users, networks, keys and billing.

ResourceAnything managed via the API (node, VM, volume, VPC, bucket …). Every resource has a desired and an actual state.

Node lifecycle#

Every node goes through a fixed lifecycle that is controlled entirely via API, portal or MCP:

StateMeaningTransition triggered by
DiscoveredDevice has sent a DHCP/boot requestPlugging in the cable
InventoriedDiscovery image has booted and reported the hardwareautomatic
PendingNo auto-adopt match; waiting for approvalautomatic
AdoptedApproval granted or an auto-adopt rule matchedPortal / API / MCP or rule
RejectedApproval deniedPortal / API / MCP
ProvisionedIdentity and certificate issued, OS image rolled outautomatic
ActiveRoles assigned and healthyautomatic
MaintenanceDrain: workloads are moved elsewhereOperator
DegradedHealth check failed; self-healing back to "Active"automatic
QuarantineIntegrity in doubtautomatic, from any adopted state
DecommissionedData securely erased, certificate revokedOperator

Key rules:

  • Unknown hardware never automatically gets access to tenant data. Discovery runs in an isolated network or mode; only adoption assigns an identity (see Boot & adoption and Security model).
  • Quarantine can be reached directly from any adopted state (Provisioned, Active, Maintenance, Degraded) – not only via "Degraded". Triggers include attestation failures, anomaly findings, a mismatched hardware fingerprint or the same node identity appearing twice; in the latter case both nodes are quarantined.
  • The way back from quarantine to "Active" requires fresh attestation and human approval.
  • Decommissioning includes verifiable erasure (BSI CON.6, ISO 27001 A.7.14) – a compliance-relevant step.

Unique selling point: zero-touch hardware onboarding, decentralized control without a central controller, multi-tenant hyperscaler services, API/portal/MCP at every level, from a Pi to the data center, and compliance by design – none of the solutions listed combines all of this.

Non-goals#

  • No in-house hypervisor, no in-house database, no distributed file system from scratch – proven components such as Cloud Hypervisor are integrated. Clarification from 2026-11-14: block and object storage based on the platform Raft and an in-house chunk layer are in-house developments (block replication using a primary-copy scheme is not a distributed file system). Ceph is not a mandatory component, only an optional external driver for data centers that already run Ceph (see Storage).
  • No API compatibility with AWS, Azure or GCP – the exception is the S3-compatible object storage; tooling integration is via OpenTofu/Terraform providers.
  • No network boot over Wi-Fi – onboarding requires Ethernet (Wi-Fi nodes possibly later via a boot stick).
  • No proprietary dependencies, not even mandatory "open core" components.
  • No Kubernetes distribution – Kubernetes is a service of the platform, not its foundation.
  • No hardware without 64-bit support – Pi 1, Pi 2 and Pi Zero W are excluded; a Pi Zero 2 W is only suitable as a witness via boot stick.
