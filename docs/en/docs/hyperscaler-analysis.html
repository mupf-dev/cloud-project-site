Purpose#

The analysis compares the service offerings of AWS, Microsoft Azure and Google Cloud with DCP's plan. It answers three questions: Which features should the platform eventually offer? How will they be implemented? And when? In total, around 230 features were examined across three areas: infrastructure; data, AI and integration; and identity, security, operations and developer tools. The analysis was accepted on 2026-11-12.

The following tables are an abridged selection of the most important categories.

Ground rule: in-house development preferred#

Since 2026-11-12 the rule is: prefer in-house development where it makes sense. The platform builds control, policy and workflow logic itself – this fits the Raft-based state, authorization with Cedar, the parity of API, portal and MCP, and tenant isolation (see Rust stack and API-first).

Components with a very large maintenance or maturity effort remain external, always integrated across a process boundary:

  • Database and protocol engines (PostgreSQL, MariaDB, Valkey, Kafka, OpenSearch, ClickHouse) – compatibility is the point here; a reimplementation would bring no benefit. Guardrail: "no database of our own" (see Vision).
  • Hypervisor, Kubernetes, container runtime – security- and kernel-critical, a large investment in maturity.
  • Inference engines – they depend on GPU kernel ecosystems (see AI platform).
  • Knowledge bases that need constant upkeep – the scanners' vulnerability databases, DLP detectors.
  • Python ecosystems such as Airflow, Spark, Jupyter or fine-tuning frameworks.

Even with external engines: control, API, tenant isolation, backup and metering are developed in-house. An exception to "no database of our own" is block and object storage, which, following a separate decision, are developed in-house (see Storage).

All components must have OSI-approved licenses. This excludes, among others, HashiCorp Vault, Packer and Nomad (BUSL), newer versions of CockroachDB, ScyllaDB and EMQX, MongoDB (SSPL), Redpanda and Restate (see License and governance).

Key gaps up to release 1.0#

The largest gaps compared with the hyperscalers, to be closed by release 1.0 or 1.x:

  1. Backup service for tenants – policies via labels, retention, immutable vaults, copy to a second site, guided restore. Particularly in demand in the homelab.
  2. Tenant observability – separate metrics and logs with a query API, alert rules as API resources, dashboards in the portal.
  3. L7 load balancer with ACME certificates – the entry-level case for almost every web service; the basis for WAF, CDN, static hosting and container serverless.
  4. Autoscaling groups and container serverless – "n identical instances behind a load balancer, self-healing".
  5. Continuous configuration compliance – assessment of the inventory with conformance packs (such as "BSI baseline"), history and automatic remediation (see Compliance requirements).
  6. Identity-bound access (bastion, zero trust) as well as a certificate service and private CA.
  7. Notification, email and workflow service as a shared cross-cutting capability instead of individual solutions per component.
  8. VPN, private endpoints, FinOps, SDKs and deployment stacks.

Object versioning and Object Lock were moved to release 1.x because they require an in-house object storage.

Selected decisions for existing building blocks#

  • Telemetry: collection, alert evaluation, notification, dashboards and the tenant-isolating query gateway are our own; storage for metrics and logs remains external. Grafana is not a mandatory component.
  • Secrets manager: our own instead of an additional product – the key hierarchy and Raft state already exist, and a second consensus service would contradict the principle of "one consensus mechanism" (see Control plane).
  • Billing: our own, since the metering data already lives in the platform.
  • Infrastructure as code: own OpenTofu provider, generated from the OpenAPI description; Pulumi via a bridge instead of a second package.
  • Container registry: zot stays (Apache-2.0, process boundary), supplemented with image scanning and signature verification at admission.
  • AI gateway: our own gateway developed in Rust (see AI platform).
