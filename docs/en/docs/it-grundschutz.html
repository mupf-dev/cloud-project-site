BSI IT-Grundschutz modeling

How DCP models the "platform" sub-domain of the information domain from the manufacturer's perspective according to Grundschutz++, maps requirements to components and evidence, and provides operators with a protection requirements template.

Adapted from: Concept 66 (BSI IT-Grundschutz modeling)

Note: Technical modeling, not legal or audit advice. The modeling is a template; responsibility for the operator's own information domain (Informationsverbund) remains with the operator.

Key decisions#

No.Decision
1The target is Grundschutz++ (BSI Standard 300-1, user catalog in OSCAL format). The IT-Grundschutz Compendium 2023 (IT-Grundschutz-Kompendium) is supplied only as a derived view for operators who still work with it – generated, not maintained by hand.
2What is modeled is the "platform" sub-domain of the information domain (Teil-Informationsverbund) from the manufacturer's perspective: 13 technical target objects, the node hardware and seven information types. The operator adopts it as a building block of its own information domain and adds location, personnel and organization.
3There is a single, versioned source for the mapping requirement ↔ Grundschutz++ requirement ↔ target object ↔ responsibility ↔ evidence. All operator artifacts are generated from it.
4References to Grundschutz++ requirements carry both keys: the human-readable ID and the stable UUID.
5The continuously updated catalog is pinned and shipped with the platform; a regular update run produces a diff report for review. No build loads the catalog live from the network.
6For assets without a matching target object category (containers, Kubernetes, KMS, distributed state) the project provides a small supplementary catalog.
7A protection requirements template with assumptions per information type and target object, in three deployment profiles, compatible with both classic BSI IT-Grundschutz and Grundschutz++.
8External checking tools (OSCAL validation) run only in CI as a separate process; the OSCAL files are produced by the project's own generator.

Who models what?#

BSI IT-Grundschutz modeling is the task of the organization that runs an ISMS – that is, the operator. The technical part, however, is the same for all installations, so the project, as manufacturer, does it in advance:

LevelWhoResult
Manufacturer templateprojecttarget objects of the platform, mapping to target object categories and requirements, implementation description per component (OSCAL Component Definition), protection requirements assumptions, suggested parameters
Operator's information domainoperatoradoption of the template, additions for sites, rooms, personnel, service providers and business processes; protection requirements, requirements package, parameters, implementation status
Use by tenantstenantfor the tenant, the entire platform is one cloud service; it models its workloads itself

For the operator, the components are applications, host systems and networks within its information domain; for the tenant, the platform is a cloud service. The shared responsibility matrix connects both views (see Compliance requirements).

Grundschutz++ in brief#

The user catalog comprises around 1,000 requirements in 20 practices – for example asset management, permissions, detection, configuration, architecture, development and business continuity management. Each requirement carries a security level (normal-SdT, i.e. normal/state of the art, or erhöht, i.e. elevated), its effect on the protection goals, associated threats, target object categories and in some cases parameters that the operator defines. Around 140 requirements carry the tag "product description" (Produktbeschreibung) – exactly the requirements that a manufacturer can provide as an OSCAL component definition. They form the mandatory scope of DCP's component definition.

About a third of the requirements have no target object category; these are mostly ISMS and organizational requirements that apply to the operator's entire information domain. Here the platform only provides data sources: implementation status from the configuration, recorded exceptions to the secure default, evidence exports for audits, prepared reporting data for incidents, and protection requirements labels on resources.

Because the catalog is updated continuously – roughly weekly – version pinning and referential integrity checks are indispensable. Third-party mapping tables are never adopted without review.

Supplementary catalog#

For assets without a matching target object category there is a small dedicated OSCAL catalog. The requirements are worded following the sentence template of Grundschutz++ and reference their origin in the Compendium or in C5. Examples:

  • The control plane SHOULD admit only nodes with the minimum trust level of the deployment profile as voting members.
  • The control plane SHOULD execute destructive actions only after quorum confirmation.
  • The control plane SHOULD replicate tenant objects only to authorized nodes.
  • Compute SHOULD start only signed or approved images.
  • Managed Kubernetes SHOULD run a separate control plane per tenant.
  • Storage SHOULD make released blocks unreadable before reuse.
  • The overlay SHOULD prevent traffic between VPCs of different tenants without explicit peering.
  • Adoption SHOULD be bound to a key generated on the device; network boot alone does not establish trust.
  • The KMS SHOULD support tenant-owned keys and crypto-shredding.
  • MCP access SHOULD treat AI agents as actors in their own right and execute destructive actions only after confirmation outside the AI client.

Mapping principle: requirement → component → evidence#

Every requirement in the catalog is mapped to at least one Grundschutz++ requirement, one target object, one responsibility and one evidence type. The background is the rule from the requirements catalog: A requirement counts as implemented only when the platform delivers automatically generated evidence.

Machine-readable maintenance#

The modeling is not maintained as a document but as structured data in the repository. The principles:

  • Single source: target objects, mappings, implementation texts, suggested parameters and the protection requirements template live in versioned, machine-readable files. Tables in documents are generated from them, not the other way around.
  • Pinned catalog: the Grundschutz++ catalog is recorded with version and checksum and shipped unchanged. A regular update run produces a diff (new or removed IDs, changed texts, security levels, categories) and flags affected mappings for review. Only after review is the new state adopted.
  • Checks in CI: schema validation, integrity of the pin, referential integrity of every cited ID, coverage (every requirement has a target object and evidence; every relevant "product description" requirement has a status), reachability of the evidence, and consistency between the defaults in the code and the statements in the mapping (policy as code).
  • Release binding: every platform version names the catalog state against which its statements apply.

Protection requirements assumptions as a template#

The template connects both methods: the classic one (BSI 200-2) with the categories normal, high and very high per protection goal, and Grundschutz++ via the security level of the requirements. The bridge: normal → only normal-SdT; high → additionally the erhöht requirements of the affected target objects plus a risk assessment; very high → additionally an individual risk analysis. All values are manufacturer assumptions that the operator confirms or changes based on its business processes.

Inheritance to target objects#

Following the maximum principle, target objects inherit the protection requirements of the information they process. Even in the standard profile this results in a risk assessment and a selection of erhöht requirements for the KMS, control plane, identity service, audit log, boot service and OS image. The project provides a prepared risk assessment for this as part of the threat model.

Deployment profiles#

ProfileTarget groupAssumptionAdditionally active (selection)
homelabprivate, labeverything normal, integrity of keys and artifacts highquarantine of new nodes, staged rollout, encryption of data at rest – because possible without extra effort
standard-c5hosting providers, companiesassumptions as abovejust-in-time administration, key splitting, non-repudiation, automatic configuration management, secure boot (where the hardware supports it), higher minimum trust levels for critical roles
erhoeht (elevated)public authorities, critical infrastructure (KRITIS)tenant data very highdedicated hardware, no overcommitment, physical segmentation, geo-redundancy, HSM instead of key splitting

The crypto profile (bsi-strict or compatible) is chosen independently; standard-c5 and erhoeht are permitted only with bsi-strict. Protection requirements labels on resources are mapped to data classes and minimum trust levels for placement – high, for example, to nodes with a TPM, very high to attested nodes or dedicated hosts.

What the operator does with the template#

  1. Define the scope and business processes.
  2. Confirm or adjust the information types; determine the protection requirements of tenant data together with the tenants or via labels.
  3. Choose a deployment profile and import the profile export into the ISMS tool.
  4. Review the parameters.
  5. Model its own parts (buildings, personnel, service providers, upstream network) and complete the risk assessment.
  6. Take over the implementation status from the platform export and confirm exceptions.
