Dienste wie bei einem Hyperscaler#

Die Plattform bietet Grunddienste, die sich an den bekannten öffentlichen Clouds orientieren. Alle Dienste sind Ressourcen derselben API und damit gleichermaßen über Portal, API und MCP nutzbar.

Drei gleichwertige Zugänge#

Jede Funktion ist über REST-API (OpenAPI), Web-Portal und MCP (Model Context Protocol, für KI-Assistenten und Agenten) verfügbar – auf jeder Ebene: Plattform, Mandant, Projekt, Ressource. Portal und MCP-Werkzeuge werden aus demselben API-Schema abgeleitet; eine CI-Prüfung verhindert, dass ein Zugang Funktionen bekommt, die den anderen fehlen. Dazu kommt das Kommandozeilenwerkzeug cpctl. Details: API-first-Prinzip.

yaml# Beispiel einer Ressource (vereinfacht)
apiVersion: compute.cloud-project.io/v1
kind: VirtualMachine
metadata:
  name: web-01
  parent: cp:global:tenant/acme/project/shop
  labels: { env: prod }
spec:                       # gewünschter Zustand
  machineType: small-2c-4g
  arch: any                 # arm64 | x86_64 | any
  image: cp:global:image/debian-13
  network: { vpc: default, subnet: web }
status:                     # tatsächlicher Zustand, schreibt nur das System
  phase: Running

Rollen#

Jeder Knoten trägt den Agenten cp-agent. Weitere Aufgaben übernimmt er über Rollen, die manuell, per Regel (etwa „alle Knoten mit mindestens zwei Platten → storage-block“) oder auf Vorschlag des Planers zugewiesen werden.

bootNetzboot-Dienst: proxyDHCP, TFTP/HTTP-Boot, Image-Cache
dnsPlattform-DNS: autoritative Zonen, DNSSEC, virtuelle IPs

observabilityMetriken, Logs, Traces

Knoten-Lebenszyklus#

Ein Knoten durchläuft einen klar definierten Lebenszyklus. Unbekannte Hardware erhält nie automatisch Zugriff auf Mandantendaten – erst die Adoption vergibt eine Identität.

  • Entdecken: Ein neuer Knoten bootet per Netz (PXE/HTTP-Boot, Raspberry-Pi-Netzboot) oder vom USB-Stick in ein Discovery-System im Arbeitsspeicher. Es schreibt nichts auf Platten und meldet einen Hardware-Steckbrief.
  • Adoptieren: Freigabe per Portal, API oder MCP – geschützt durch einen Bestätigungscode, ab höherer Ausbaustufe zusätzlich durch TPM-Attestierung. Der private Knotenschlüssel verlässt den Knoten nie.
  • Bereitstellen: Installation des signierten OS-Images (oder Diskless-Betrieb), Ausstellung des Knotenzertifikats, Aufnahme in Underlay-Netz und Gossip.
  • Betreiben: Rollen zuweisen, Wartung mit Drain, Selbstheilung bei Störungen.
  • Stilllegen: nachweisbares Löschen, Widerruf des Zertifikats, Rotation der Gossip-Schlüssel – mit Löschnachweis für die Compliance.

Updates und Releases#

  • Unveränderliches OS-Image (cpOS): /usr ist schreibgeschützt und per dm-verity gesichert, / ist flüchtig, Zustand liegt in einer verschlüsselten Partition.
  • A/B-Updates mit automatischem Rückfall: Das Update wird in den inaktiven Slot geschrieben. Erst wenn ein Health-Gate nach dem Neustart grün meldet, gilt der neue Stand; sonst fällt der Knoten nach wenigen Versuchen selbstständig auf den alten Slot zurück.
  • Signierte Release-Bündel: Images, Erweiterungen und Agent werden als Bündel mit Manifest, Prüfsummen, SBOM und Signaturen ausgeliefert; Update-Metadaten folgen dem Prinzip von TUF (The Update Framework) mit Offline-Wurzelschlüsseln.
  • Rollout-Controller: Updates laufen in Wellen mit Kanarienvogel-Stufe, Wartungsfenstern und maxUnavailable. Höchstens ein Voter je Zelle wird gleichzeitig aktualisiert, der Leader zuletzt. Schlägt ein Gate fehl, hält der Rollout an.

Plattform-DNS#

Die Rolle dns (Dienst cp-dnsd) beantwortet die Namen der Plattform und der Mandanten autoritativ, signiert Zonen mit DNSSEC, vergibt virtuelle IP-Adressen (VIPs) für Plattformdienste wie Portal und API und schützt sich mit Ratenbegrenzung gegen Missbrauch. Innerhalb der Mandantennetze beantwortet jeder Host DNS, DHCP und Metadaten lokal – ohne zentralen Dienst im Datenpfad. Mehr: Plattform-DNS.

Identität und Mandanten#

  • Hierarchie Plattform → Mandant → Projekt → Ressource, optional Ordner innerhalb eines Mandanten.
  • Eigener, schlanker OIDC-/OAuth-2.1-Autorisierungsserver mit Passkeys zuerst, Föderation zu bestehenden Identitätsanbietern (OIDC/SAML).
  • Kurzlebige, sender-gebundene Tokens, die auf jedem Knoten lokal geprüft werden. Autorisierung über einen Beziehungsspeicher im Stil von Zanzibar plus Cedar-Richtlinien für Bedingungen und Leitplanken.
  • Strikte Trennung zwischen Betreiber und Mandanteninhalten: Betreiber sehen Metadaten, Inhalte nur über einen begründeten, befristeten und protokollierten Zugriffsantrag.
  • KI-Agenten sind ein eigener Akteurstyp; sie handeln mit der Schnittmenge aus Nutzerrechten, Token-Umfang und Agenten-Leitplanken.
  • Mandanten-Löschung mit Krypto-Löschung und signiertem Löschnachweis.

Speicher#

  • Block-Volumes über einen eigenen Rust-Datenpfad: lokal (dm-thin + dm-crypt) und repliziert (zwei bis drei Kopien) – derselbe Pfad von 2 bis zu tausenden Knoten.
  • Metadaten in der vorhandenen Raft-Gruppe der Zelle, Nutzdaten nie im Konsens.
  • Mandantenverschlüsselung am Compute-Knoten: Speicherknoten sehen nur Chiffrat.
  • Objektspeicher S3-kompatibel hinter einem eigenen S3-Frontend mit Rechteprüfung und Quoten.
  • Dateispeicher per NFS auf replizierten Volumes, im Netz des jeweiligen VPC.
  • Platzierung über Fehlerdomänen, Reife-Gate vor dem Einsatz replizierter Volumes für Mandantendaten.

Netzwerk#

  • Underlay: ein WireGuard-Interface je Knoten, innen IPv6-only; Peers kommen ausschließlich aus dem replizierten Zustand. Zusätzlich ein Pre-Shared-Key aus einem Post-Quanten-Verfahren.
  • Mandanten-Overlay cp-vnet: eigene Steuerung im Agenten, Linux-Kernel-Datenpfad (VRF je VPC, VXLAN im WireGuard-Tunnel, nftables) – keine zweite Konsensdatenbank.
  • Sicherheitsgruppen zustandsbehaftet, eingehend standardmäßig gesperrt.
  • Nord-Süd-Verkehr über die Rolle network-gateway: NAT, Floating IPs, L4-Load-Balancer; im Homelab per Layer-2-Bekanntgabe, im Rechenzentrum per BGP.
  • Drei Ausbaustufen: flat (ein LAN), vlan, routed (L3 bis zum Host).

Sicherheit und Compliance#

  • Vertrauenskette vom Secure Boot mit eigenen Schlüsseln der Installation über Measured Boot und TPM-gebundene Plattenverschlüsselung bis zu mTLS zwischen allen Diensten.
  • Knotenidentität mit kurzlebigen Zertifikaten aus einer internen PKI, Vertrauensstufen T0–T4, Remote Attestation.
  • Kryptografie nach BSI TR-02102, Krypto-Agilität und Fahrplan für Post-Quanten-Verfahren.
  • Lückenloses Audit jeder Änderung, Break-Glass-Verfahren mit Protokollierung.
  • Compliance-by-Design: 36 Architekturleitlinien, Anforderungskatalog aus ISO 27001, BSI IT-Grundschutz, BSI C5, DSGVO, NIS2 und Cyber Resilience Act; Nachweise werden exportierbar.
  • Lieferkette: reproduzierbare Builds, SBOM je Artefakt, signierte Releases, VEX für Schwachstellenbewertungen.

KI-native Plattform#

  • Eigene API-Gruppe für Modelle, Modellversionen, Inferenz-Endpunkte, AI-Gateways, Budgets, Guardrails, Vektorindizes und Wissensbasen.
  • Inferenz-Engines (zunächst llama.cpp, dann vLLM) laufen als signierte Container hinter einem einheitlichen Adapter; dedizierte Endpunkte in MicroVMs mit durchgereichtem Beschleuniger.
  • Zwei Betriebsmodelle: dediziert je Mandant oder geteilt/serverless mit Abrechnung je Token – ohne mandantenübergreifenden Cache.
  • Beschleuniger (GPU, NPU) als Scheduler-Ressource, Scale-to-zero mit lokalem Modell-Cache, Modelle als signierte OCI-Artefakte mit Cache je Zelle.
  • Die Plattform selbst ist per MCP steuerbar; Agenten der Mandanten nutzen Plattform-Werkzeuge mit eingeschränkten Rechten.
  • KI-Compliance als Querschnitt: Modellkarten, Herkunft, Kennzeichnung, Protokollierung nach EU AI Act, Abbildung auf BSI AIC4.
